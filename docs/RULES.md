# NINMODS — Project Rules & Engineering Standards (`docs/RULES.md`)

> **বাধ্যতামূলক নীতি (Mandatory Directive):** এই প্রোজেক্টে কাজ করার আগে যেকোনো এআই এজেন্ট (AI Agent) বা ডেভেলপারকে এই ডকুমেন্টের প্রতিটি ধারা শতভাগ মেনে চলতে হবে। কোনো কাজের শুরুতেই সম্পূর্ণ কোডবেস এন্ড-টু-এন্ড রিভিউ করতে হবে এবং বাস্তব ও পরীক্ষিত ফলাফল ছাড়া কোনো কাজ সম্পন্ন ঘোষণা করা যাবে না।

## ১. স্ট্যান্ডার্ড জাভাডক / ডক্সিজেন কমেন্টিং নীতি (Javadoc / Doxygen Style Comments ONLY)

* **ব্যানার ও ডেকোরেটিভ কমেন্ট সম্পূর্ণ নিষিদ্ধ (Zero ASCII Banners):**
  কোডের ভেতর কোনো প্রকার ব্যানার লাইন যেমন:
  ```java
  // =========================================================================
  // State Query Helpers (Restores state safely from Engine / Preferences)
  // =========================================================================
  // -------------------------------------------------------------------------
  /* ####################################################################### */
  ```
  লেখা সম্পূর্ণ নিষিদ্ধ।

* **স্ট্যান্ডার্ড ডকুমেন্টেশন স্টাইল (Official Javadoc / Doxygen Format):**
  প্রতিটি মেথড, ফাংশন, কনস্ট্রাক্টর ও ক্লাসের পূর্বে অফিসিয়াল জাভাডক (Java/Kotlin) বা ডক্সিজেন (C/C++) ফরম্যাটে কমেন্ট লিখতে হবে:
  ```java
  /**
   * Retrieves the stored or live toggle state of a feature.
   *
   * @param context Context used to resolve shared preferences.
   * @param featNum Native feature index.
   * @param featName Feature name or key.
   * @param defaultVal Default state if no prior state was saved.
   * @return Stored or live boolean state of the feature.
   */
  public boolean getToggleState(Context context, int featNum, String featName, boolean defaultVal) {
      // Implementation
  }
  ```
  - অবশ্যই `@param` দিয়ে প্রতিটি প্যারামিটারের উদ্দেশ্য ব্যাখ্যা করতে হবে।
  - অবশ্যই `@return` দিয়ে রিটার্ন ভ্যালুর ধরন ও তাৎপর্য ব্যাখ্যা করতে হবে।
  - যদি এক্সেপশন থ্রো করার সম্ভাবনা থাকে, তবে `@throws` উল্লেখ করতে হবে।

## ২. প্রতিটি ফাইলের প্যাকেজ ডিক্লারেশন ও ইমপোর্ট হেডার বাধ্যতামূলক অডিট নীতি (Mandatory Package & Import Header Audit)

* **কাজে হাত দেওয়ার আগে ও পরে ইমপোর্ট অডিট:**
  যেকোনো ফাইলে কাজ করার সময় বা কোড এডিট করার পূর্বে ও পরে, এজেন্টকে অবশ্যই ফাইলের সর্বপ্রথমে থাকা `package` নাম এবং প্রতিটি `import` স্টেটমেন্ট লাইন-বাই-লাইন পুঙ্খানুপুঙ্খভাবে মিলিয়ে দেখতে হবে।
  ```java
  package com.ninmods.main.menu;

  import android.graphics.drawable.GradientDrawable;
  import android.os.Build;
  import android.os.Handler;
  import android.os.Looper;
  import android.text.TextUtils;
  import android.util.DisplayMetrics;
  import android.util.TypedValue;
  import android.view.Gravity;
  import android.view.MotionEvent;
  import android.view.View;
  import android.view.ViewGroup;
  import android.view.WindowManager;
  import android.widget.AdapterView;
  import android.widget.ArrayAdapter;
  import android.widget.FrameLayout;
  import android.widget.SeekBar;
  import android.widget.Spinner;
  import android.widget.Switch;
  ```
* **কোনো প্যাকেজ হেডার বাদ দেওয়া সম্পূর্ণ নিষিদ্ধ:**
  জাভা বা কোটলিন ফাইলে কোনো অবস্থাতেই ফাইলের শুরুর প্যাকেজ ডিক্লারেশন (যেমন `package com.ninmods.main.menu;`) বাদ পড়া চলবে না। প্যাকেজ বাদ পড়লে ক্লাস ডিফল্ট প্যাকেজে চলে যায় এবং সম্পূর্ণ রেফারেন্স নষ্ট হয়।
* **প্রয়োজনীয় প্রতিটি ক্লাসের জন্য সঠিক ইমপোর্ট নিশ্চিত করা:**
  কোডে ব্যবহৃত প্রতিটি অ্যান্ড্রয়েড ফ্রেমওয়ার্ক ক্লাস বা উইজেটের জন্য প্রয়োজনীয় ইমপোর্ট নিশ্চিত করতে হবে, যাতে কোনো `cannot find symbol` বা কম্পাইলেশন এরর তৈরি না হয়।
* **অকেজো বা অনুপস্থিত ইমপোর্ট প্রতিরোধ:**
  কোনো ডুপ্লিকেট, অকেজো বা অনির্ভরযোগ্য ইমপোর্ট ফাইলে রাখা যাবে না।

## ৩. সব এজেন্টের জন্য বাধ্যতামূলক সম্পূর্ণ কোডবেস এন্ড-টু-এন্ড রিভিউ (Mandatory Full Code Review)

* **কাজে হাত দেওয়ার আগে সম্পূর্ণ কোড রিভিউ:**
  - যেকোনো এআই এজেন্টকে কোনো ফাইল এডিট করার পূর্বে সম্পূর্ণ সম্পর্কিত কোডবেস ম্যানুয়ালি রিভিউ করতে হবে।
  - বিচ্ছিন্ন কোনো ফাংশন বা লাইনে পরিবর্তন করে কাজ শেষ ঘোষণা করা সম্পূর্ণ নিষিদ্ধ।
  - **সম্পূর্ণ পাইপলাইনের ইন্টারকানেকশন ম্যাপিং (Trace the complete path):**
    `User Event / Floating Menu` ➔ `MenuController` ➔ `JNI Bridge (MenuPreferences.Changes / NativeBridge)` ➔ `C++ Engine (Menu.cpp / FeatureTable.h)` ➔ `Kernel Driver (/dev/BYNb Ring-0 IOCTL)` ➔ `ESP / Aimbot Processing` ➔ `EspOverlayService.kt`
    এই সম্পূর্ণ ট্রানজিশন চেইন পুঙ্খানুপুঙ্খভাবে মিলিয়ে দেখতে হবে যাতে কোনো এক স্তরের পরিবর্তন অন্য কোনো স্তরে ব্রেক না ঘটায়।

## ৪. ১০০% কার্নেল ড্রাইভার নীতি (Kernel Driver ONLY for ninmods)

* `ninmods` এর সমস্ত মেমরি অপারেশন, ইএসপি এবং এইমবট **১০০% আসল কার্নেল ড্রাইভার (RT/QX Ring-0 Character Device `/dev/BYNb`)** এর মাধ্যমে পরিচালিত হবে।
* কার্নেল ড্রাইভার ছাড়া কোনো প্রকার অল্টারনেটিভ ফলব্যাক, ড্রাইভারলেস মেমরি রিড বা বিকল্প প্রসেস হ্যাক সম্পূর্ণ নিষিদ্ধ।
* `ninlite` হলো **Internal Engine Mode**, যা রুট প্রসেসের মাধ্যমে `process_vm_readv` লিনাক্স সিসকল ব্যবহার করে পরিচালিত হয়। কোড পরিবর্তন করার সময় এই দুই চ্যানেলের আচরণ সবসময় কঠোরভাবে পৃথক রাখতে হবে।

## ৫. একক কেন্দ্রীয় মেনু সিস্টেম নীতি (Single Central Unified Menu System)

* সমস্ত ব্র্যান্ড UI (`nin`, `ninlite`, `bull`, `cross`, `delta`) একটি মাত্র কেন্দ্রীয়, অফিসিয়াল ও নির্ভরযোগ্য কন্ট্রোলার ফাইল ব্যবহার করবে:
  `com.ninmods.main.menu.MenuController.java`
* কোনো ব্র্যান্ডের জন্য আলাদা মেনু-লজিক, স্লাইডিং আচরণ বা কার্যকরী কোড তৈরি করা যাবে না।
* প্রতিটি ব্র্যান্ডের UI স্বতন্ত্র ডিজাইনে রেন্ডার হতে পারবে, তবে ড্র্যাগিং, টাচ ক্ল্যাম্পিং, সুইচ টগল, স্লাইডার এবং ড্রপডাউনের সমস্ত ইভেন্ট কেন্দ্রীয় `MenuController` থেকেই নিয়ন্ত্রিত হবে।
* মেনুর অপশন বা ফিচার লিস্ট জাভায় হার্ডকোড করা সম্পূর্ণ নিষিদ্ধ; এগুলো C++ ইঞ্জিন থেকে JNI (`GetFeatureList()`, `SettingsList()`) এর মাধ্যমে ডায়নামিকভাবে আসবে।

## ৬. জিরো ফেক বা ডামি কোড (Zero Fake / Dummy Code)

* প্রজেক্টে কোনো ফেক ডেটা, ডামি অফসেট, মক স্ট্যাটাস বা কৃত্রিম ড্রয়িং রাখা সম্পূর্ণ নিষিদ্ধ।
* প্রতিটি ড্রাইভার, মেমরি রিড/রাইট এবং ফিচার লিনাক্স ও অ্যান্ড্রয়েড ওএস লেভেলে শতভাগ আসল (Genuine) এবং কার্যকরী হতে হবে।

## ৭. জিরো হার্ডকোডেড ব্র্যান্ডিং (Zero Hardcoded Branding / 100% Dynamic White-label)

* কোনো ব্র্যান্ডের নাম, ডিফল্ট আইডেন্টিফায়ার বা কোনো স্ট্যাটিক ব্র্যান্ডিং টেক্সট কোডের ভেতর লেখা সম্পূর্ণ নিষিদ্ধ।
* সমস্ত ব্র্যান্ডিং, টাইটেল, লাইসেন্স এবং কনফিগারেশন সরাসরি ডাটাবেজ বা রিমোট সার্ভার থেকে ডায়নামিকভাবে আসবে।

## ৮. একক কেন্দ্রীয় অফসেট ফাইল (.env Architecture in C++)

* সমস্ত গেম অফসেটের নিয়ন্ত্রণ থাকবে মাত্র ১টি ফাইলে: `gameoffsets.h` (C++)।
* কোনো অফসেট একাধিক ফাইলে ছড়িয়ে রাখা বা ডুপ্লিকেট করা সম্পূর্ণ নিষিদ্ধ।

## ৯. নেটিভ-ফার্স্ট ESP আর্কিটেকচার (Kotlin is UI Only, C++ Handles Everything)

* ESP-এর জন্য কোটলিন অংশে থাকবে মাত্র ১টি একক UI ফাইল: `EspOverlayService.kt`।
* কোনো মেমরি রিডিং, মেট্রিক্স, WorldToScreen প্রজেকশন বা এনিমি ট্র্যাকিং কোটলিনে হবে না; সমস্ত প্রসেসিং ১০০% নেটিভ C++ এ সম্পন্ন হবে।

## ১০. স্থায়ী ৯০ অটো-ইনক্রিমেন্টাল ভার্সনিং প্রটোকল (Strict Permanent 90.X Versioning)

* প্রতি আপডেটে ডেসিমাল সংখ্যা ধারাবাহিকভাবে ১ করে বাড়বে (`V90.87` ➔ `V90.88`...)।

## ১২. ইউজারের সুস্পষ্ট নির্দেশ ছাড়া পুশ বা ক্লাউড বিল্ড সম্পূর্ণ নিষিদ্ধ (Strict Zero Push Without Explicit Confirmation)

* **ব্যবহারকারী নিজে মুখে 'পুশ করো' না বলা পর্যন্ত গিটহাবে কোনো পুশ করা যাবে না:**
  সমস্ত কোড পরিবর্তন ও আপডেট লোকাল প্রজেক্ট ডিরেক্টরিতে সংরক্ষিত থাকবে। ব্যবহারকারী যখন নিজে অনুমোদন দেবেন ও বলবেন "পুশ করো", শুধুমাত্র তখনই পুশ করা যাবে।

## ১৩. কঠোর ডাউনলোড ফোল্ডার লগিং নীতি (Zero Root SDCard Clutter)

## ১৪. ৩০০ লাইনের ভেতরের ফাইলের জন্য ১০০% ফ্রেশ রিরাইট নীতি (Complete Clean Rewrite for Files Under 300 Lines)

* যদি কোনো ফাইলের সাইজ ৩০০ লাইনের ভেতর হয়, তাহলে কোনো ভাঙা-চোরা আংশিক (snippet) এডিট করা সম্পূর্ণ নিষিদ্ধ।
* সম্পূর্ণ ফাইলটি একবারে ফ্রেশ কোড দিয়ে নতুন করে লিখতে হবে যাতে কোড ১০০% নিঁখুত ও অক্ষত থাকে।

## ১৫. জিরো টাইমার ও ১০০% খাঁটি লিনাক্স ওএস মেকানিজম নীতি (Strict Zero Artificial Timers — 100% Genuine Linux Native System)

* **কোনো সিস্টেমে কোনো কৃত্রিম টাইমার নয় (Zero Artificial Timers Across ALL Systems):** প্রজেক্টের কোনো সিস্টেমে (জাভা/কোটলিন, সি++, সকেট, থ্রেড, লাইফসাইকেল বা ব্যাকগ্রাউন্ড সার্ভিস) কোনো প্রকার কৃত্রিম টাইমার, কাউন্টডাউন, বা টাইমআউট ব্যবহার করা সম্পূর্ণ নিষিদ্ধ।
* **টাইমার-ভিত্তিক কৃত্রিম সিস্টেম সম্পূর্ণ বর্জন:** সকেটের জন্য কোনো `SO_RCVTIMEO` / `SO_SNDTIMEO`, শেলের জন্য কোনো থ্রেড জয়েন কিলার টাইমার (`join(10000)`, `join(25000)`), হ্যান্ডশেক কাউন্টডাউন টাইমার (যেমন ৬০ বার লুপ কাউন্টডাউন), বা কৃত্রিম বিলম্ব লুপ কোডে রাখা যাবে না। কোনো কৃত্রিম টাইমার শেষ হওয়ার অজুহাতে কোনো সকেট কানেকশন ক্লোজ করা, ইঞ্জিন বন্ধ করা, বা রুট প্রসেস কিল (`destroyForcibly`) করা যাবে না।
* **১০০% খাঁটি লিনাক্স ও অ্যান্ড্রয়েড ওএস নেটিভ মেকানিজম (100% Genuine Linux Native Architecture):** সমস্ত অপারেশন লিনাক্স ও অ্যান্ড্রয়েডের আসল অপারেটিং সিস্টেম মেকানিজমে পরিচালিত হবে:
  - **Blocking POSIX UNIX Domain Stream Sockets:** ডেটা আদান-প্রদানে লিনাক্স কার্নেলের স্বাভাবিক স্ট্রিমিং ও ব্লকিং বাফার মেকানিজম কাজ করবে। কার্নেল নিজে থ্রেড শিডিউল ও ওয়েকআপ করবে।
  - **Natural Process Lifecycle:** প্রসেস পর্যবেক্ষণ ও প্রসেস সমাপ্তি ট্র্যাক করতে লিনাক্স ওএস মেকানিজম যেমন `process.waitFor()`, `waitpid()`, এবং `/proc/[pid]` ব্যবহার করতে হবে।
  - **Cross-UID Signal Permission:** অ্যান্ড্রয়েডে ভিন্ন UID-এর প্রসেসের অস্তিত্ব যাচাই করতে লিনাক্স সিসকল `kill(pid, 0)`-এর সাথে `errno == EPERM || errno == 0` সঠিকভাবে হ্যান্ডেল করতে হবে (ভুল টাইমআউট বা ভুল রিটার্ন ধরে প্রসেসকে ডেড ঘোষণা করা সম্পূর্ণ নিষিদ্ধ)।
  - **Native Event-Driven UI:** অ্যান্ড্রয়েড লাইফসাইকেল এবং ভিউ ট্রানজিশনে কোনো কৃত্রিম `postDelayed` টাইমার নয়; অ্যান্ড্রয়েডের ন্যাচারাল লাইফসাইকেল ইভেন্ট ও লোডারের ইভেন্ট কিউ (`Handler.post()`) ব্যবহার করতে হবে।
